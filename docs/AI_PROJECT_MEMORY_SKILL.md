# AI Project Memory の使い方（作成・更新・引き継ぎ）

このファイルは、Claude / Codex / ChatGPT / Cursor / Grok など**どのAIが来ても同じ手順で引き継げる**ようにするための方法書です。
ルール本体は `AGENTS.md`（全ツール共通の唯一のルール置き場）。このファイルはルールを足さず、「記憶の扱い方」だけを決めます。

> チャット履歴は正式な作業記録ではない。GitHub の Project Memory が、複数AI・複数チャット間の**共通セーブデータ**。

## 1. 3つのファイルの役割

| ファイル | 何を書くか | 何を書かないか |
| --- | --- | --- |
| `docs/AI_HANDOFF.md` | **いまの状態**。本番URL、完了したPhase、未完了、次にやること、変更禁止領域、ハマりどころ | 細かい作業ログ（PRに書く） |
| `docs/DECISION_LOG.md` | **長く守る判断とその理由**。将来のAIが勝手に変えると困るもの | すぐ陳腐化するCSS修正・一時デバッグ |
| `docs/AI_PROJECT_MEMORY_SKILL.md` | この方法書 | プロジェクト固有の事実 |

## 2. 作業を始めるとき（毎回）

1. `git status --short --branch` / `git remote -v` で場所と既存変更を確認する。
2. `AGENTS.md` → `README.md` → `docs/AI_HANDOFF.md` → `docs/DECISION_LOG.md` → このファイル → 対象コード・テストの順に読む。
3. 最新 `main`、関連する merged PR、同じファイルを触る Open / Draft PR を確認する。
4. 次を自分の言葉で把握してから手を動かす: 現在地点 / 完了Phase / 未完了 / 制約 / 本番URL / 関連repo / 変更禁止領域 / 過去の判断。
5. Project Memory やコードを読めば分かることを、オーナーに再質問しない。

### 情報が食い違ったとき

1. 現在の `main` のコード / merged PR
2. `DECISION_LOG.md` の明示的なオーナー判断
3. `AI_HANDOFF.md`
4. 現在の公式一次情報
5. 過去チャットやAI自身の記憶

これは「実装の現状」を決める順位であり、人物情報が正しいと認定する順位ではない。人物事実が一次情報と Decision Log で衝突したら、**勝手に上書きせずオーナーに確認する**。

## 3. 更新するタイミング

- 大きなPhaseが完了・mergeしたら、**必ず** HANDOFF の更新要否を確認する。
  - 例: 新機能、新しいrepo / URL、本番変更、新しい人物プロフィール事実、新しい運用ルール、完了Phase、新しい未完了。
- 長く守るべき判断・将来のAIが変えると困る判断が生まれたら DECISION_LOG に1件追記する。
  - 例: canonical URL、source of truth、固定表示順、privacy方針、意図的な例外、architecture判断、AI分業。
- 日々のコンテンツ追加（NEWS 1件、写真1枚）では HANDOFF を更新しない。PR本文で十分。

## 4. 書き方

- HANDOFF は「上書きして最新に保つ」。古い状態は消してよい（履歴はgitにある）。冒頭の「最終更新」日付を必ず更新する。
- DECISION_LOG は「追記のみ」。過去の判断を変えるときは消さずに新しい行で「D-xx を置き換え」と書く。
- 1判断 = 日付 / 判断 / 理由 / 影響範囲。理由を省かない（理由がないと次のAIが「不要」と判断して消す）。
- 推測で埋めない。未確認は「未確認」と書く。

## 5. 公開repoに書いてはいけないもの

このrepoは**公開**です。Project Memory も公開されます。

- 私的DM・私信・承認メッセージそのもの、非公開の人間関係、恋愛感情・関係性の推測
- 住所・電話番号・私的連絡先・家族情報
- token / credential / secret、非公開の受け渡しURL・Drive ID・署名URL
- 制作者（オーナー）の職業・勤務先を特定できる表現
- 未承認の二次素材（配信スクショ・切り抜き等）のファイルやURL

非公開で残すべき引き継ぎ（素材の承認状態など）は、オーナーの非公開Notion / 非公開repoへ。ここには「どこを見ればよいか」だけを書く。

## 6. 引き継ぎを受けたAIへ

- 最初の返答で「HANDOFFで把握した現在地」を3〜5行で示すと、オーナーは説明し直さなくて済む。
- 終わったら「何をしたか / PR / 検証 / 未確認 / merge と本番反映の状態 / HANDOFF更新の要否」を報告する。
